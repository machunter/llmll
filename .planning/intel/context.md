## Topic: SAFE-ARG — the first non-fail-closed defect

- source: docs/design/finding-arg-position-false-safe.md (Rev 2 — FIXED and RELEASED in v0.14.73)
- One line: the type channel lets a `bytes[32]` value satisfy a `bytes[64]` parameter when it passes through one unannotated function, and the verifier then asserts `bytesLen(b) = 64` as a ground fact from that parameter's declared type, discharging the index-in-bounds obligation against a premise that is false.
- Severity recorded as **FALSE SAFE** — a `verified` verdict on a memory-safety obligation that does not hold; not fail-closed. Every prior member of the FQ-RESULT-SORT-1 family exits 1 with a solver crash; this one reports `SAFE`, writes a `.verified.json`, and records `display_level.level = "verified"` with `body_faithful: true` and a `verified_hash`.
- Eight-line reproduction: `mk32` returns `bytes[32]`; `mid2` is the unannotated laundering hop; `consume` declares `b: bytes[64]` with `pre (and (>= i 0) (< i 64))`; `caller` passes `(mid2)` to `consume`. `llmll check` passes; `llmll verify` reports SAFE.
- Five-step chain with a witness each: (1) a declared `bytes[n]` return over a body of another length is rejected (`P1_direct`, `P5_noncall`); (2) one unannotated hop launders the same mismatch past the type channel (`P2_wildcard`, `P3_declared_lie`, `Q1_argpos` — all `check` clean); (3) the binder's declared type becomes a ground fact (`bytesLenReft`); (4) the index obligation is discharged from that fact; (5) the verdict is `SAFE` and is persisted.
- Root of step 2: `compatibleWith (TVar _) _ = True` together with `collectTopLevel` registering an unannotated return as `TVar "?"`.
- Found by professor review of `ret-resolve-proposal`, 2026-07-29; the chain was measured jointly with the language-team over four review rounds.
- Rev 2 exists because the Rev 1 discriminant "which implementation proved dead as specified" — exact equality with `TVar "?"` missed the `freshenFnType` instances `?$N`.

## Topic: the FQ-RESULT-SORT-1 review, two rounds

- source: docs/design/finding-fq-result-sort-default-review.md (two rounds, standalone review; not folded)
- The defect: the contract channel derives the sort of the `result` binder from the optional `-> RetType` annotation and falls back to `FQInt` when absent, while the type channel derives it from the synthesized body type (`TypeCheck.hs:992`, `fromMaybe bodyType mRet`). Where the two disagree, the emitted `.fq` is ill-sorted and liquid-fixpoint crashes.
- "The direction is right in both revisions. The disagreements are about how wide the trigger set is, what actually contains the defect, and how far into the compiler the corrected derivation should reach." Round 1 reviewed Rev 0, which scoped the fix to the emitter; round 2 reviewed Rev 1, which widened it into the type environment.
- Context located that bounds the fix: `FQFile` has five fields and **no well-formedness-constraint slot**, and no `wf` block is emitted anywhere in `compiler/src/` (`FQKVar` exists in the predicate type but nothing constructs one). `ContractEnv`'s third slot is the callee return type and is a `Maybe`. `Module.extractContracts` stores the raw `mRet` into `meContracts`, so `synthRet` is not on that path. `Module.toExport` computes `fromMaybe (TVar "?") mRet`, so **the module interface has no representation for an unannotated function's return type**. `typeCheckWithCache` runs over the module's statements and `buildModuleEnv` builds the interface from `stmts`, not from the result. `checkStatements` is a two-pass scheme (pass 1 `collectTopLevel`, pass 2 body checking) — the circularity that forced the Rev 1 type-environment row to be withdrawn.

## Topic: the RET-BRANCH-PREF adjudication

- source: docs/design/ret-branch-pref-proposal-review.md (Rev 0, standalone review; not folded)
- Unusual ordering: the adjudication was delivered *before* Rev 0 was written, so the proposal already folds these findings; the file preserves the adjudication as a standalone artifact and rules on the one divergence Rev 0 recorded against it.
- F-1 (MAJOR): the routed objection — that the rule "will need a real join the first time both branches are concrete-but-different" — is already answered by the code. `TypeCheck.hs:1327-1331` emits `if branches have different types: …` and then picks `thenType` anyway. LLMLL already has an arbitrary bias at this join point and already treats a genuine disagreement as a diagnostic rather than a lattice operation. **Bite: dissolves the objection.**
- F-2 (MAJOR): the lattice invoked was the wrong one. The operation is the meet in the **precision** order (Siek and Taha 2006; Garcia, Clark and Tanter, POPL 2016), not a least-upper-bound in the subtype order, and the precision order is orthogonal to subtyping. **Bite: the move is recognized and named, not ad hoc.**
- F-3: reclassified from **soundness** to **scope** and the soundness classification **withdrawn**. Pushed further than Rev 0 did: for the unrestricted rule to produce a false SAFE rather than a crash, the wildcard branch's reflection would have to be well-sorted at the inferred type while denoting a different type; the wildcard branch is a call whose binder is sorted at the callee's own `tau_ret`, so a genuine disagreement is ill-sorted and fails closed. The one residual shape needs an unfilled hole body, and refilling a hole re-runs verification. **So no complete program reaches a false SAFE through this rule.**
- F-4 (MINOR): spec/code drift at the `if` reconciliation (`LLMLL.md §3.4.6:399`). Route independently; complicates the spec text, does not block.
- Two build conditions, both cheap and both already in Rev 0: a corpus `.fq` byte-diff against a rebuilt pre-change compiler (the suite passed with HOLE-RET's twelve-function regression present, so it will not catch this either), and a negative fixture `(if c (g x) 1)` with `g` a different unannotated function, which must still synthesize the wildcard.
- Recorded as a pattern rather than an incident: "This is the second time on this line that a claim of mine was narrowed by measurement rather than argument, and both times the measurement was cheap."
- Open questions for the language-team: **none.**

## Topic: the RET-RESOLVE review, four rounds

- source: docs/design/ret-resolve-proposal-review.md (rounds 1–4; rounds 1–2 folded into Rev 1/Rev 2, rounds 3–4 produced SAFE-ARG and WILD-ASSUME instead of proposal changes)
- Round 1, seven findings against Rev 0. The `if`-join preference without a side condition reintroduces the guess Stage 1 was narrowed to exclude — condition it on same-SCC membership. `tau_ret` gates admissibility, so the pass changes tier assignment and not only sorts. The deferral of the type-environment fix is justified on grounds the spec does not supply: SCC-ordered binding-group typing is part of the Damas-Milner core, and the undecidable neighbour is *polymorphic* recursion inference, which is not what the fix needs. The wildcard is the gradual dynamic type without casts, so the `L_mono` residue is a predicted consequence. SC2 quantified over diagnostics only — strengthen to a sandboxed state. The brief-versus-verifier asymmetry widens (round 3 correction: the brief reads the *raw* `mRet`, so the asymmetry is wider and older than stated). `⊔` is not a join.
- Round 1 recommendation: take the proposal. The stratification it describes — a fixpoint over a fixed base-type skeleton downstream of type inference and forbidden from influencing acceptance — is how refinement inference is staged in Liquid Haskell.
- Round 2: `tau_ret` reaches `augmentContractPost` via the definition-site call sites, so the pass changes the **effective postcondition**. Refinement aliases *are* synthesized, contrary to the code comment, so `tau_body` can be a `TCustom` whose predicate folds into the effective post as a new obligation; the available direction is `verified → refuted`, strictly stronger than the two directions Rev 1 enumerated. Also: recording a channel is insufficient, because the fact's truth depends on a producer whose annotation was never validated — the invariant needs the producer's verification status in its antecedent.
- Round 3: the latent false SAFE, and **a recommended fix that was wrong**. "My recommended fix was wrong and the language-team refuted it with measurement." `P3_declared_lie` shows the false fact is injected from *declared* returns too, identically at v0.14.71 and v0.14.72, so the proposed revert targets the widening and not the defect; `P5_noncall` shows no call-free laundered lie exists.
- Round 4: the live false SAFE. `Q1_argpos` verifies SAFE at both v0.14.71 and v0.14.72 and writes a `.verified.json`. The defect is not latent, is not gated on any hygiene fix, and predates the entire FQ-RESULT-SORT-1 line. Consequent findings: WILD-INDEX as stated in Rev 3 was incomplete (keying on checking positions misses argument passing, which is where the damage is); `indexed(τ)` was an enumeration in search of a criterion, and the criterion is "contributes a VC assumption that no obligation discharges", which is FACT-AG inverted; the anti-laundering invariant covers records and not assumptions.
- Literature answer on recording repair-shaped demotions: keep it out of the lattice. §5.3.4's meet ranks evidence strength at a point in time, and overloading it with history costs comparability. The correct reading is belief revision (contraction, not the assertion of a weaker claim), operationally a justification-based truth-maintenance record; the assurance-case literature versions the argument rather than re-grading the claim. In-project the device exists as `codegen_semantics_version`, though the stamp has no reader, so it records incomparability without enforcing it.
- Convergence note: "Four rounds, four reading paths, one defect. … None of the four steps would have found it alone." The channel count for `tau_ret` moved 1 → 2 → 4 → 4-plus-parameters, each increment found by reading rather than by deriving the consumer set from the emitter — the argument for having the engineer re-derive the set mechanically.

## Topic: the SPEC-AGREE-1 review

- source: docs/design/spec-agreement-review.md (Rev 0, standalone review; not folded)
- **Status at HEAD:** the proposal has been revised to Rev 1 and folds this review. Three of the review's own figures are superseded by measurement and are recorded here as history, not as current claims: F-1's "roughly a fifth to a quarter" is measured at **10.6%** (9/85); the Q2 framing of the datatype-capable backend as carrying "its own Lever A dependency" is refuted (zero array and zero measure abstentions in the measured corpus); and the review's Context claim that `examples/tftp_rfc1350/` holds only `VERIFICATION_SCOPE.md` (so stage K had not run) is false at HEAD, where that directory holds `roots/` and `wave/`. See INFO-4 and INFO-14 in `.planning/INGEST-CONFLICTS.md`.
- Headline verdict: "The idea is right, the epistemology needs rebuilding, and the shipped-primitives claim in §1 and §6 does not survive contact with the code."
- Two findings the review labels BLOCKER in its own vocabulary. **F-1**: the applicability claim is false — three strictly nested fragments, not one, putting the comparable set at roughly a fifth to a quarter of the `Encoded` set on the motivating run, which also refutes the effort table. **F-2**: dropped parameter and return refinements manufacture false disagreement, because `buildSubsumptionFQ` compares over the *unrestricted* sort while `Feasibility.buildQuery` folds refinements into the effective query; two contracts agreeing on every well-typed input but differing on a region the refinement already excludes would be reported non-equivalent, generating a witness at an unreachable input.
- F-3: `contractSubsumes` maps everything that is not `FQSafe` to `False`, so a rate computed on that boolean cannot distinguish "the readings differ" from "liquid-fixpoint fell over". The information is discarded, not absent.
- F-4: the lattice is a **product** order (contravariant in the precondition, covariant in the postcondition), and the three-point output projects it onto one axis. **Precondition strengthening is the dangerous case** — a stronger `pre` narrows the domain on which the obligation fires, the function still verifies, the contract still carries its `:source`, and no downstream instrument fires because the excluded inputs are exactly the ones no mutant exercises. Zaremski and Wing (TOSEM 1997) have the finer taxonomy.
- F-6: the strictly-ordered case can be dispositioned mechanically, three ways, all already in the repo — feasibility on the stronger contract (`sat` means definitively over-strong), good-twin refutation, and mutant kill differential. "It is the highest-value change available and it costs nothing new."
- F-7: Knight-Leveson is the right citation and the wrong stopping point. The models that say what to do next (Eckhardt and Lee; Littlewood and Miller) show failures correlate through a common **difficulty function**, and **forced methodological diversity can drive the covariance negative**. The largest leak is not T3 but the **inventory obligation gloss** — a prior formalization of the same clause in prose, fed identically to all N arms, sitting at the same layer as the artifact being produced. Cheapest high-value levers: adversarially different framings; withholding the gloss from at least one arm and reporting agreement with and without it.
- F-9: T3's resolution toward comparability is right but understated and mislocated. Comparability requires only **sort** agreement, while the freeze as described also fixes the state decomposition including the arms of the outcome sum — and those arms are a formalization of the clause's case analysis. For C1 rows the frozen signature can contain most of the answer. Measure the leak by re-running one arm against the same signature with constructor and field names mechanically replaced by opaque `A0..An`.
- F-13 (observation): witness adjudication relocates human judgment; it does not replace human audit or reduce the quantity of judgment. It changes the task from generation to discrimination and the failure mode from silent omission to recorded decision. **The tool is strongest where the problem is weakest** — sharpest on C2 arithmetic rows where side-by-side audit is already easiest, and absent on C1 transition rows where audit is hardest and the pipeline's documented failure lives. The defensible frame is process-level.
- Recommendation ranking: (1) build it with named changes and a re-sequenced build — recommended; (2) build only the comparison CLI as a developer tool and defer the experiment — acceptable if F-1 comes back very low, since the CLI has standalone value for `refine` hygiene and detecting accidental contract duplication; (3) do not build — **rejected**, because the disagreement half is sound evidence independent of any independence assumption and a C2-only defeater generator beats zero.
