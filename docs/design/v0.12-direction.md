## Thesis

v0.12 completes the refinement metatheory of record (REF-META-2..5), opens the Bundle B effect-row track at stage B0, and widens the core grammar's non-int `EVar` surface conditional on `FixpointEmit.hs` solver support. None of these are architectural hypothesis bets requiring an empirical gate before shipping; all three extend the v0.11 foundation incrementally. The sequencing discipline: spec-track items (REF-META-2..5) proceed in parallel under the standard LT-proposal → doc-lead path with no empirical gate; engineer-track items (non-int widening) gate on solver support; language-design items (Bundle B) are staged with B0 shipping as spec+engineer work and B1 requiring its own LT-proposal before the engineer builds.

v0.11's one remaining open item entering v0.12: the `def-logic` removal (LT-INV Rev 4). v0.12 makes `def-logic` a parse error under all grammar modes. The 17 pending `.llmll` S-expression files (engineer scope) must complete migration before v0.12 ships that change.

## 1. REF-META-2..5 — Refinement Metatheory of Record

REF-META-1 (settled Rev 2, promoted 2026-05-27) ships the checking-mode inference rule, non-goals list, and soundness statement of record. Four items remain:

| Item | Content | Priority | Path |
|---|---|---|---|
| **REF-META-2** | Solver-completeness statement: which QF-LIA-shaped predicates are guaranteed to discharge vs which fall back to `?proof-required`. Characterizes the automatic/manual obligation boundary. | P2 | LT proposal → doc-lead → `LLMLL.md §5.3.3` |
| **REF-META-3** | Predicate well-formedness rule: when is `(where [x: T] p)` a legal type definition; restrictions on `p` (no free variables outside `x`; no function-valued sub-expressions at the top-level predicate position; measure-function axiomatization discipline). | P2 | LT proposal → doc-lead → `LLMLL.md §3.4` |
| **REF-META-4** | Erasure theorem with construction-side discipline: refinement predicates are erased at codegen; what construction-side discipline (witnessed at the SMT-check boundary) preserves their meaning at the Haskell runtime boundary. | P3 | LT proposal → doc-lead → `LLMLL.md §3.4` |
| **REF-META-5** | Full typing judgment: the **type-assignment judgment** (local type inference, Pierce–Turner) into which REF-META-1's checking-mode rule embeds, covering all introduction/elimination forms for the refinement-aliased type surface. *Not* a "complete bidirectional system" — non-hole checking is synth+unify (= type assignment, D–K §3.1); the one genuine checking rule is hole-goal recording; no subsumption (non-goal #1). | P3 | LT proposal → doc-lead → `LLMLL.md §3.4/§5` |

**Sequencing.**

REF-META-2 and REF-META-3 are independent and should be drafted in parallel — neither is a prerequisite of the other. REF-META-4 requires REF-META-3 (erasure requires a WF predicate definition to erase from). REF-META-5 requires REF-META-1..4 (the full judgment must cite each sub-rule). The dependency graph:

```
REF-META-2 ── (parallel) ── REF-META-3
                                │
                            REF-META-4
                                │
                            REF-META-5
```

All four are spec-track only — no compiler work; no schema bump; no `trust_report_version` change. The checking-mode rule at `LLMLL.md §3.4.1` and the two-phase implementation correspondence (existing `TypeCheck.hs` + `FixpointEmit.hs`) already cover the implementation; the proposals fill the spec record.

**External anchors.**
- REF-META-2: `LLMLL.md §5.3.3/§5.3.5`; [`compiler/src/LLMLL/FixpointEmit.hs:188-194`](../../compiler/src/LLMLL/FixpointEmit.hs) (unbounded-integer smtlib2 theory selection).
- REF-META-3: Vazou et al., *Refinement Types for Haskell* §3 (the `p ∈ Bool` WF side condition); Liquid Haskell `Data.Refined` WF discipline.
- REF-META-4: `LLMLL.md §3.4:229-241` (current erasure prose); [`compiler/src/LLMLL/CodegenHs.hs`](../../compiler/src/LLMLL/CodegenHs.hs) type-alias resolution (`TCustom` → underlying `T`).
- REF-META-5: Pierce & Turner, *Local Type Inference* (TOPLAS 2000) — the lineage LLMLL instantiates (local, per-call-site instantiation); Damas–Milner, *Principal Type-Schemes* (POPL 1982) for the inference core. ## 2. Refinement-aliased non-int widening

**Origin.** LT-INV §2 deferred: "relaxation to refinement-aliased strings (`Word`, `Letter`), refinement-aliased ADT-fields, and refinement-aliased lists is a v0.12+ widening conditional on `FixpointEmit.hs` support landing."

**Gate condition.** The current [`compiler/src/LLMLL/FixpointEmit.hs:188-194`](../../compiler/src/LLMLL/FixpointEmit.hs) selects the `Int` SMT theory for all predicate emission. Non-int refinements require axiomatizing `string-length` and `list-length` as integer-valued uninterpreted functions inside the `Int` theory, with refinement obligations discharged as QF-LIA on their images. This is path (a) — no theory extension required, stays within the auto-discharge boundary.

Path (b) — a theory extension to `Str` or `Array` in the liquid-fixpoint call — is deferred. It risks escaping the QF-LIA auto-discharge boundary and is not the v0.12 candidate.

**V0.12 action.** After REF-META-3 settles, the language-team drafts the non-int widening LT proposal specifying:

1. **Phase 1 (v0.12):** Admit `EVar-refined-string` and `EVar-refined-list` in the core grammar where the refinement predicate involves only `string-length` / `list-length` respectively and QF-LIA arithmetic on their integer images. Both restricted to measure-function refinements; character-position or element-identity predicates excluded and remain in `def-shell`.

2. **Phase 2 (v0.13+):** Refinement-aliased ADT-fields (record projections as measure functions). Requires `FixpointEmit.hs` support for user-defined measure functions — larger compiler change, not v0.12 scope.

**Prerequisite.** REF-META-3 must be settled before this widening proposal is drafted. The predicate WF rule determines which predicates over non-int types are legal and must be resolved before the proposal can specify the measure-function axiomatization side condition.

**Not empirically gated.** Non-int widening is a soundness-track extension, not a hypothesis-track one. The gate is the verifier confirming the claim for the admitted predicate shape — not an LLM-behavior experiment. If `string-length`-only refinements turn out to produce nonlinear arithmetic in the `Int` theory (e.g., predicates over concatenated strings where both operand lengths appear), the admitted predicate shape must be tightened; the REF-META-2 solver-completeness statement provides the framework for stating that boundary.

## 3. Bundle B — Effect rows on `Command`

**Reclassification.** Bundle B was reclassified from the indexed-types research track into its own v0.12+ scheduling line per the v0.11 direction memo §4. Row-polymorphic effects are HM extended with row polymorphism — Leijen, *Extensible Records with Scoped Labels* (2005); Koka; Frank — decidable HM extension, not dependent types. The cost class is meaningfully different from `Vect n a` / GADTs.

**Staged path.**

| Stage | Content | v0.12 role |
|---|---|---|
| **B0** | Function-level effect *summaries* in obligation reports: derive per-function effect sets from `ModuleEnv` capability declarations and body inspection; surface as a new field alongside the three existing channels (type, contract, trust). No syntax change; additive obligation-report extension. | **In scope for v0.12 spec + engineer build.** Additive obligation-report enrichment analogous to the v0.10 OBLIG-* work; adds a fourth channel (effect obligations) without a type-system change. |
| **B1** | Explicit row-annotated `Command {stdout, fs.read} a` types in function signatures (opt-in annotation, typechecker-checked). Requires new syntax. | **LT proposal in v0.12; engineer build gated on a B1-native experiment.** Drafted and professor-reviewed in v0.12. The original "B0 experiment gates the B1 build" condition is **retired** — F-B0-3 (postmortem-007) showed a single-file B0 experiment cannot measure the effect (B0 is informationally redundant where capabilities are syntactically evident). Engineer build is now authorized by a **B1-native** experiment: does an effect-typed *signature* improve capability-correct composition (measured against the design-reference set — Liquid Haskell `.spec` / F\* effect interfaces). The B1 LT proposal proceeds independently. See [`bundle-b0-cross-module-addendum.md`](bundle-b0-cross-module-addendum.md) §3–§4. |
| **B2** | Row-polymorphic effect inference: `Command {ρ} a` with row type variables. Algorithm W extension required. | **v0.13+ at earliest.** |
| **B3** | Effect-aware contracts: `seq-commands : Command {e1} a → Command {e2} b → Command {e1 ∪ e2} b`. Requires B2 and contract-engine integration. | **v0.13+ at earliest.** |

**B0 specification.** The B0 obligation-report field derives a per-function *effect summary* — the set of capability labels reachable from a function's body, derived from: (a) the function's own `wasi.*` / `haskell.*` / `c.*` import declarations in `ModuleEnv`; (b) transitive reachability through called functions' effect summaries. Informational in B0: does not affect trust tier or verification outcome. Coarse capability labels only: `stdout`, `fs.read`, `fs.write`, `net.http`, `random`, `crypto`. Value-indexed paths (`fs.read "/data"`) are excluded — that is the existing capability-declaration mechanism's slot.

**B0 empirical instrument — RETIRED as the B1 gate (F-B0-3, 2026-06-15).** The original plan made a B0 obligation-report experiment the authorization condition for the B1 engineer build. F-B0-3 ([`experiments/minimal-agent/findings/postmortem-007-b0-pilot.md`](../../experiments/minimal-agent/findings/postmortem-007-b0-pilot.md)) disproved its premise: in single-file LLMLL every capability is syntactically evident (namespaced `wasi.*`), so a surfaced report-side summary carries no information the agent did not already have — the pilot (`004`, the `001-two-agent-auth` harness having proven unsuitable) returned an uninformative null. B0's value concentrates at **opaque boundaries** (cross-module imports, delegate/scaffold, FFI), which the single-file first-round harness cannot exercise. The B1 engineer build is therefore gated on a **B1-native** experiment instead (effect-typed *signature* vs. the design-reference set); the B1 LT proposal proceeds independently. The cross-module half of B0's value shipped separately as a soundness fix and B1 prerequisite — see [`bundle-b0-cross-module-addendum.md`](bundle-b0-cross-module-addendum.md).

**Guardrail (inherited from v0.11 direction memo §4).** Start with coarse capability labels — **not** value-indexed paths. Value-indexed labels push toward singleton types; the existing capability mechanism already handles path / scope authority at the import declaration. Keep that separation deliberate.
